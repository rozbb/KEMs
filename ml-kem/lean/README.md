# ML-KEM formal verification

This folder contains the machinery necessary to formally verify the `ml-kem` crate (and the parts of
`module-lattice` it uses) against a Lean specification of ML-KEM (FIPS 203). The pipeline is as follows:

1. Transpile the Rust to Lean with [Aeneas](https://github.com/AeneasVerif/aeneas). This outputs to `ExtractedRust/`
2. Prove the top-level theorems, showing that the Rust implementation matches the Lean specification. These are in `TopLevelTheorems.lean`

The specification is [Wychelean](https://github.com/rozbb/wychelean)'s, vendored in `Wychelean/` (see its README).

# Transpiling Rust to Lean

In order to prove correctness of Rust, it must first be translated to Lean. This is already done for you, and stored in `ExtractedRust/`. But if you made code changes and want to re-transpile, then simply run `extract_rust_to_lean.sh` in the root of this crate.

`ml-kem` is generic over its parameter sets via `typenum`, which Aeneas can't handle generically. So we extract one copy of the code per parameter set: Charon monomorphizes everything reachable from the `aeneas_entry` module of `src/lib.rs` (only built with `--cfg aeneas`). Aeneas doesn't support monomorphized crates out of the box, so `scripts/fix_llbc.py` patches Charon's output up first.

# Building Lean

To verify the theorems, you need to build the Lean project. To do this, follow these steps:

1. Install [elan](https://github.com/leanprover/elan), the Lean toolchain manager
2. `cd lean`
3. Run `lake exe cache get`. This will fetch the Mathlib cache and reduce build times by a lot.
4. Run `make prove-mlkem` to prove the top-level theorems and check that all axioms have been audited. This will take a while.

# What is not proved

Some details are outside our formalization:

1. `sha3`, `shake`, `hybrid-array`, `typenum`, `ctutils`, and `core` are dependencies, and thus are not extracted. We model their behavior in `ExtractedRust/{Types,Funs}External.lean`, the hash functions using the SHA-3 functions of the spec. These models are trusted, see `TrustBase.lean`
2. We cannot prove in Lean that anything operates in constant-time
3. Deserialization of expanded decapsulation keys (`from_expanded`) is not covered
4. The theorems that sample a matrix assume `SampleNTTHalts`: rejection sampling (Algorithm 7) halts on every input, i.e. SHAKE128's output always contains enough values `< q`. This is overwhelmingly likely, but unprovable in practice. Where it fails, the Rust loops forever

# File layout

| Path                              | Contents                                                                                         |
| ----------------------------------|--------------------------------------------------------------------------------------------------|
| `TopLevelTheorems.lean`           | The set of theorems we prove about `ml-kem` |
| `TrustBase.lean`                  | Every axiom we use in our proofs. This is executed automatically by `make prove-mlkem`, and will error out if any unexpected axiom is found. Also describes the other things we trust. |
| `Wychelean/`                      | The ML-KEM spec (FIPS 203), with SHA-3 (FIPS 202) and the utilities it depends on. Vendored from upstream |
| `ExtractedRust/{Types,Funs}.lean` | **Autogenerated. Do not edit.** This is the Aeneas output. Run `../extract_rust_to_lean.sh` |
| `ExtractedRust/*_Template.lean`   | **Autogenerated. Do not edit.** Aeneas's list of the external declarations we must model |
| `ExtractedRust/TypesExternal.lean`| Models of the external types |
| `ExtractedRust/FunsExternal.lean` | **Autogenerated. Do not edit.** Models of the external functions, generated by `scripts/gen_funs_external.py` |
| `scripts/fix_llbc.py`             | Patches Charon's monomorphized output so that Aeneas accepts it. Run by `../extract_rust_to_lean.sh` |
| `MlKem/Properties/`               | All the stuff needed for proving top-level theorems, layered bottom-up: `Defs` (how Rust values are read as spec values), `Arith`, `Poly`, `Ntt`, `Compress`, `Encode`, `Hash`, `Sample` (the building blocks), `SpecLemmas` (facts about the spec alone), `Pke` (K-PKE), `Kem` (ML-KEM), and `TopLevel` (the per-parameter-set top-level theorems). Each layer's `@[step]` lemmas are what the layers above use. The ML-KEM-768 and -1024 parts of `Pke` and `Kem` are the ML-KEM-512 proofs with the sizes substituted. |
